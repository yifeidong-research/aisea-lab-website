## [nov23-4] People page converted to a collapsible accordion

### Context
User pointed out the People page has grown too long (many entries now across 4 categories) and
readers have to scroll a lot to find someone — asked to first show a compact list, then reveal
full details on click. Cline asked which interaction pattern (inline accordion / dedicated
per-person page / modal popup); user deferred to Cline's professional judgement.

### Design decision
Chose **native HTML `<details>`/`<summary>` accordion** (one per person) over a per-person
routed page or a JS modal, because: (1) this is a static Astro site with no client-side JS
framework and a deliberately minimal/editorial aesthetic — `<details>` needs zero custom
JavaScript, works identically with JS disabled, and is natively keyboard/screen-reader
accessible (no custom ARIA/focus-trap code to write or maintain); (2) a per-person routed page
would add real routing complexity (dynamic `[slug].astro`, URL slugs, `profileUrl` vs. internal
link disambiguation) for content that's only a few short paragraphs — not justified; (3) a modal
overlay would need escape-key/backdrop-click/focus-trap JS that doesn't exist anywhere else in
this codebase, and modal patterns feel more "app-like" than the "MIT CSAIL/Stanford HAI-style
editorial" aesthetic the site deliberately pursued (see the visual-design decision in
`systemPatterns.md`).

### What was done
- `src/pages/people.astro`: each person's `<li class="person-card">` now wraps a
  `<details class="person-details">`. The always-visible `<summary class="person-summary">`
  contains the photo, name (`<h3>`, no longer wrapped in `profileUrl` link — the link moved
  inside the expanded body instead, see below), role line (with the existing
  entryYear/Started-Starting suffix), and a `<span class="person-toggle">` (CSS-only `+`/`−`
  glyph via `::before` content, flipped by the `[open]` attribute selector). The hidden
  `<div class="person-detail-body">` holds a "UTS profile ↗" link (if `profileUrl` is set) above
  the bio paragraphs, plus a `Bio coming soon.` placeholder note for anyone with photo/role but
  no bio yet (e.g. people added without a confirmed bio) — avoids an awkward empty expand.
- `src/styles/global.css`: restructured `.people-list li` from a flex row to a block wrapper;
  `.person-summary` now carries the flex layout (photo + text + toggle) and
  `cursor: pointer`/hidden native marker (`::-webkit-details-marker`); `.person-toggle` is a
  1.6rem bordered square with `+`/`−` content swapped via the `[open]` attribute; expanded body
  is indented to align under the text column (`padding-left: calc(5.25rem + 1.25rem)`, matching
  the photo width + gap). Updated the `25rem` mobile breakpoint (previously `.people-list li {
  flex-direction: column }`) to target `.person-summary` with `flex-wrap: wrap` instead, and
  removed the now-redundant indent on mobile.
- No changes to `src/content/site.ts` — purely a `people.astro` + CSS change, reusing all
  existing `Profile` data as-is.

  `dist/people/index.html` (one per person across all 4 categories).

## [nov21-7] Created a single shared workflow for adding People-page entries

### Context
User asked (in plan mode) whether it would be more efficient to create separate predefined
"skills"/workflows for each People category (Core Member, Collaborator, PhD Student, Master of
Research Student), or whether an LLM's reasoning/procedure is the same with or without a
predefined skill.

### Cline's analysis (shared with user before implementing)
Inspected `src/content/site.ts` (`Profile` type + `people` array) and `src/pages/people.astro`
(`categoryOrder`). Concluded the procedure for adding any person is identical regardless of
category — only the `category` string literal differs — so 4 separate skill files would be
near-duplicate boilerplate with no efficiency gain, and would create a maintenance burden (a
procedure change would need editing in 4 places instead of 1). Recommended **one shared,
parameterized workflow** instead, covering: the "never fabricate, omit bio instead of
placeholder" rule; the `category` union type + `categoryOrder` update needed only when
introducing a genuinely new category; the photo-file naming/path convention; the established
dual-role pattern (two `Profile` entries sharing a name/photo — see Megan Zhou, Yuhong Shi); and
the `npm run check && npm run build` verification step. Framed the actual value of a skill as
consistency/determinism and avoiding re-discovery cost each session, not new reasoning
capability — which does not scale with the *number* of near-identical skill files. User approved
switching to act mode to implement this single-workflow plan.

### What was done
- Created `.clinerules/workflows/add-person.md` — a 7-step workflow: (1) gather confirmed-only
  facts, (2) check/extend the `category` union + `categoryOrder` if a new category is needed,
  (3) handle optional photo (naming convention, placeholder fallback), (4) check for dual-role
  pattern, (5) append the `Profile` object(s) to `site.ts` matching existing bio
  string-vs-array style, (6) verify via `npm run check && npm run build`, (7) update the memory
  bank per the standard end-of-session procedure.
- No code/content changes — this is a process/workflow file only, `.clinerules/workflows/` was a
  new subfolder (previously only `.clinerules/memory-bank.md` existed).
